# The Vibe Manifesto

*On writing down what you mean*

---

### I. The problem

We were promised that we could describe what we wanted and a machine would build it.
We described. It built. What it built was no better than a guess.

The guess was often good. Sometimes it was great. But it was never *ours*, because we never
fully said what we wanted. We said what we wanted *to feel like*. That is a vibe, and a vibe
cannot be checked.

We do not accept this in other parts of life! A recipe does not say "add some flour, bake
until it feels done." It says **200g flour, 180°C, 25 minutes**. You can follow it. You can
check that you followed it. You can tell, afterwards, whether it worked.

### II. The insight

What if software worked like a recipe?

Not a description of an outcome, but **a list of steps**. Each one small. Each one exact.
Each one done in the order written. The machine does not interpret the steps. It *executes*
them.

We believe this is new. We have looked, briefly, and found nothing like it.

### III. The principles

**1. Order is everything.**
A rule written first happens first. Nothing is reordered for vibes.

**2. Say what kind of thing you mean.**
A number is a number. A list is a list. Declare it, and the declaration is binding.

**3. Guarantees beat formats.**
If you promise a number and write `"twelve"`, you meant twelve. Holding someone to a
promise is not the same as rejecting how they phrased it. This is strongly-loose typing:
strict about *what*, generous about *how*.

**4. Name the things you'll need again.**
Anything worth remembering deserves a name. Named vibes are how a program remembers.

**5. Repetition should be written once.**
"Do this three times" is one rule, not three. "Do this for every item" is one rule, not
however many items there are.

**6. Check what must be true.**
A vibe check is a promise the program makes to itself. If the promise breaks, stop.
Carrying on regardless helps nobody.

**7. Ambiguity is labelled, never hidden.**
When you genuinely can't be exact, say so, *in a marked place*: `%...%` or `#prompt`.
A vibe in a labelled box is a specification. A vibe everywhere is a mood.

**8. Every step is inspectable.**
You can see what your rules became at every stage. No black boxes. (There is a large
language model in the middle, but you can read everything it says, which is the same thing.)

**9. If it doesn't build, it isn't done.**
Programs are compiled by real compilers. When they fail, the failure is fed back until they don't.
Feelings are not a build system.

### IV. The objections

*"This is just programming."*
Programming is a word for something people used to do. This is writing rules. The fact
that the rules then become a program is a coincidence we are comfortable with.

*"You still use AI for most of the work."*
A calculator does most of the arithmetic. Nobody says the accountant didn't do the accounts.

*"Strongly-loose typing is a contradiction."*
So is "jumbo shrimp". Everyone orders it anyway.

### V. The commitment

We will write down what we mean.
We will do it in order.
We will check our work.
We will not vibe code.

*— the Vibe team*
